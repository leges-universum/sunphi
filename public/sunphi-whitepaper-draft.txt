1. PROJECT & WHITEPAPER
Status: Working draft
Purpose, participants, design commitments, and what exists today.

What SunPhi proposes
SunPhi is a proposed peer-to-peer system for transferring sun(φ) tokens. Participants would hold their own signing keys, while network nodes store verifiable fragments of token state. The project explores adaptive storage and recipient-signed transfers.
The project name is SunPhi. The token symbol is sun(φ), using the lowercase Greek letter phi. Running a node must not require buying or staking tokens. Owning tokens and operating a node are separate roles.

Three roles
Role | Responsibility
Owner / sender | Authorizes a transfer with the current owner’s private key.
Recipient | Checks the intended transfer and signs receipt.
Storage node | Stores and serves assigned fragments. Holding fragments does not grant token ownership.

Current evidence
A sequential local transaction model has passed seven tests. It uses a single in-memory arbiter and is a reference for expected behavior. It does not implement independent network agreement, real signatures, fragment coding, or token issuance.
The public website and these documents are available. A public test network, wallet installer, token sale, and production protocol are not yet available.

How to read this documentation
Design requirement identifies intended behavior. A scenario is a calculation under stated assumptions. An open decision has no approved value. A measured result must identify executable code, parameters, environment, and test outcome.
This working whitepaper records the design and its open questions. It is not an issuance prospectus, an audit opinion, or a commitment to a launch date.

2. TOKEN ANATOMY & RECOVERY
Status: Proposed record format
What sun(φ) contains, what is fragmented, and which protections address which kinds of loss.

A token is an accepted ownership record
The permanent identifier names one issued asset; its accepted state identifies who may authorize the next transfer. Copying the bytes does not create another issued token. Purchase-time issuance must admit every identifier exactly once within the selected cumulative cap of 100 million. Tokens are not minted in advance. The network admission proof and record format remain unimplemented; a serial purchase ledger only models the required gates.
The private signing key is never in the token or its fragments. The token is not a secret string that belongs to whoever assembles it.

Main object: stored at rest and fragmented
Component | Purpose
Network and format version | Separate protocol versions, networks and signing domains.
Permanent token ID | Links ownership revisions to the same issued asset, for example token 123.
Ownership revision and owner | Names the accepted state and public key authorized to spend it.
Last completed credit time | Bound to the signed receipt; interpreted with accepted-state evidence.
Recent transfer history | Baseline: ten records binding parties, transfer IDs and signatures. Ten is not a proven security optimum.
Accepted-state evidence | Establishes issuance admission and current ownership beyond a short history window. Its distributed proof format remains unimplemented.
Main hash | Commits to canonical serialized content, including signatures but excluding its own hash field. Algorithms and binary format remain open.

Temporary second part: only in transit
In transit: mainHash–reservationHash · At rest: main object only
A separate, unfragmented reservation binds the main hash, expected revision, token ID, transfer ID, sender, intended recipient and sending time. The sender signs that payload. The reservation hash identifies the complete signed record; the two hashes do not replace the underlying records.
The main hash stays unchanged from sending until completed credit. A completed receipt changes owner, credit time and history, producing a new main hash. There is no permanent “free” marker. Terminal receipt or cancellation evidence must still be retained for replay protection.

How fragments are formed
- Serialize the main object canonically and compute its hash.
- Encode into n fragments, recoverable from k valid distinct fragments. Include main hash, token revision, coding generation, fragment index and verifiable integrity metadata.
- Place fragments across the defined holder set. Codec and placement implementation are pending.
- Recover fragments from one version and coding generation; verify their integrity and the reconstructed hash. Duplicate copies of one fragment do not count toward k.
- Recoding unchanged content changes storage metadata, not ownership. A newer timestamp alone does not establish the accepted current state.
- Reconstruction recovers data only. It supplies neither the recipient’s private key nor permission to credit.
Follow the transaction: #/transaction
Erasure coding: RFC 5510: https://www.rfc-editor.org/rfc/rfc5510.html

Signatures and hashes: no circular dependency
The sender signs the canonical reservation payload excluding its signature field. The recipient signs a receipt payload binding the same token, main hash, reservation, transfer ID, parties and receipt time, again excluding its own signature field. The new main object can then include that signed receipt and receive a new hash.
Receipt time must be covered by the signature. A recipient signature is cryptographic authorization, not an arbitrary random mark; some schemes are deterministic. SunPhi has not finalized its signature suite.
Signature reference: RFC 8032: https://www.rfc-editor.org/rfc/rfc8032.html

Protection against loss: scope and limits
Event | Protection / limit
Some nodes disconnect | Redundancy permits recovery while k valid distinct fragments remain available. Correlated outages require separate analysis.
Old node reconnects | Verify accepted current state before retiring stale fragments. Keep the last recoverable encoding until replacement is safe.
Someone copies the token | The copy contains no private key. Signature checks and unique state acceptance must prevent unauthorized or conflicting spends.
Receipt acknowledgement is lost | Retrieve accepted status by transfer ID. A missing response does not authorize refund.
Private key is lost | Public fragments cannot recover it. Secure key backup or a separately designed recovery scheme is needed.
Key is stolen or wrong recipient signed | Fragmentation cannot reverse an otherwise valid authorization.
All recoverable data and backups disappear | Recovery is impossible. This design does not promise zero loss.

3. TWO-CIRCUIT TRANSACTION
Status: Workflow specification
Payment → sending time → reservation. Fragments → receipt time → recipient signature → accepted credit. Every gate has a different job.

Circuit 1 · authorize and reserve
Broadcasting a reservation does not prove that every peer received it. Unique reservation acceptance among independent nodes is required; random storage placement does not itself implement it.
Stage | Token 123: Ivan sends to Anna
1. Payment instruction | Identify Ivan, accepted main hash H7, intended recipient Anna and unique transfer T. H7 is an illustrative label.
2. Sending time and signature | Ivan signs a reservation request binding the time, both parties, T and H7.
3. Accepted reservation | Accept only one conflicting reservation. Ivan cannot make another accepted spend while T is pending. Main M7 / H7 remains unchanged; the second part carries the reservation.

Circuit 2 · reconstruct, sign and credit
A local signature is not global finality. Publication, exclusive acceptance and durable placement still require a distributed implementation. The diagram illustrates requirements; it does not execute a payment.
Stage | Recipient-side action
4. Assemble fragments | Recover M7 from k valid distinct fragments of one coding generation and verify H7. Data is recovered; the transaction is not complete.
5. Verify and record receipt time | Check Ivan’s authority and the current accepted reservation T naming Anna. Put receipt time in the payload to be signed.
6. Recipient signature | Anna signs with her private key. Someone who merely assembled the public token cannot sign as Anna under the signature scheme’s security assumptions.
7. Accepted credit | Publish candidate M8 / H8 naming Anna. Verify and uniquely accept credit instead of cancellation, with required durable storage. Only then show a spendable balance.

Reliability is attached to each gate
n = 5, k = 1, q = 0.8 → P(insufficient fragments) = (1 − 0.8)^5 = 0.032%
This illustrative result describes only reconstruction, not illicit acceptance or lifetime loss. The strict any-1% reference is n=N, k=ceil(N/100), conditional on a suitable codec and valid distinct fragments.
The two circuits are linked checks, not independent lotteries. Multiplying probabilities of two groups does not prove this transaction secure.
Workflow gate | What it establishes
Fragment availability · stage 4 | P(X < k), X ~ Binomial(n,q), estimates insufficient valid fragments for one object at one snapshot, assuming independent equally available holders.
Authenticity · stages 2, 5 and 6 | Signature verification binds the exact record to an authorized key. The availability formula does not measure forgery.
Recipient binding · stages 5 and 6 | Reservation and receipt must name the same recipient and transfer. Fragments do not authorize credit.
Freshness and exclusivity · stages 3 and 7 | A distributed acceptance rule must exclude conflicting reservations, credit and cancellation. That mechanism remains unimplemented.
Durability · stage 7 onward | New state must survive churn and recoding. Repair, checkpoints and shared failures need testing.
Adjust the reconstruction assumptions: #/probability

What a copied token can and cannot do
An outsider may reconstruct H7, but replacing Anna with Boris in Ivan’s signed reservation invalidates the signature. The outsider also needs Anna’s private key to sign her receipt. Stale copies must fail the accepted-current-state check.
A malicious owner can genuinely sign two conflicting requests. Preventing both from being accepted requires unique reservation and finality rules. Random storage, timestamps and recipient signatures alone do not supply those rules.
The intended invariant is one spendable owner and never both accepted credit and cancellation for the same reservation. It depends on correct signatures, exclusive acceptance, replay protection and durable state. Seven tests of a serial reference model check local transitions; they are not a proof across hostile independent nodes.

Disconnects, expiry and return
A timer requests resolution; it cannot unilaterally restore the sender’s balance. Credit and cancellation must be mutually exclusive. A partition may delay completion: rejecting an unverified transition protects safety, not uninterrupted availability.
Last known stage | Safe action
Reserved; no signed receipt | Remain pending. Expiry may permit a cancellation request under network rules.
Fragments reconstructed | Still pending: having the data permits neither credit nor refund.
Receipt signed; response lost | Outcome may be unknown. Retrieve accepted status; do not infer failure from silence.
Credit accepted; acknowledgement lost | Anna owns the token. Replaying T returns its existing result.
Cancellation accepted | Ivan may spend again. Advance accepted reservation-state evidence and reject later receipts for cancelled T.

4. HOW THE NETWORK WORKS
Status: Proposed architecture
Peer discovery, token state, fragment placement, and recovery.

Separate ownership from storage
The main token object contains its persistent identifier, owner-related state, recent transfer history, and the timestamp of the last completed receipt. A hash commits to the serialized main object. The private signing key is never part of this object.
A token at rest has only its main part. In transit, a separate reservation record accompanies it. This temporary record binds the main hash, transfer identifier, sender, recipient, and send time. The proposed two-part representation can be displayed as mainHash–reservationHash. Hashes identify records; they do not replace the records or their signatures.

Proposed data flow
- Discover peers through multiple routes and establish a defined holder snapshot.
- Find fragments for one accepted token version and one encoding generation.
- Verify fragment integrity, then reconstruct and verify the main object.
- Check ownership, reservation, recipient, and the accepted state-transition evidence.
- After an accepted receipt, distribute fragments of the new main object and retain recovery material until replacement is safe.

Torrent-style transport
Peer-to-peer discovery and fragment exchange take inspiration from torrent systems. BitTorrent’s DHT uses routing tables and iterative peer lookup; it does not require every lookup to scan every participant.
Discovering peers and reconstructing data do not by themselves select one outcome between conflicting transfers. SunPhi still needs an explicit, tested rule for accepting a unique reservation, receipt, or cancellation.
BitTorrent BEP 5: DHT protocol: https://www.bittorrent.org/beps/bep_0005.html

Versions and timestamps
The main part records the last receipt time; the temporary reservation records the send time. A node must associate each timestamp with the signed record, content hash, and version it belongs to. It must not combine fragments merely because they carry similar timestamps.
The largest observed timestamp is a freshness hint, not proof that no conflicting or newer accepted state exists elsewhere. Clock rules and verifiable state acceptance remain open protocol work.

Safe changes in network size
N refers to a defined snapshot of eligible holders for a storage epoch. Nodes cannot assume that their current peer list is an exact global count.
Recover old data using its original threshold before recoding. Verify complete new placement and its manifest before retiring old fragments. A drop in online nodes does not make an old encoding recoverable with a smaller threshold.
On restart, reconcile against verified current state before removing stale fragments. Keep the last usable encoding if migration or recovery is incomplete.

History size scenario
Object bytes = 200 + 256 × h + C
For comparison only, assume a 200-byte header and 256 bytes per retained transfer. C is the unknown size of additional accepted-state evidence. The resulting sizes before C are 456 bytes for h=1, 1,480 for h=5, and 2,760 for h=10.
These are assumptions, not a wire format or measured memory use. The separate reservation, indexes, repair copies, transport, and proof structures can add overhead. Keeping fewer signatures is not evidence of equal security.

Per-node storage scenario
Ideal payload per node = S × B / k
Assume S=100 million separate token objects, each B=4,096 bytes, with n=N=1 million and k=10,000. The ideal packed payload is 40.96 MB per node. If each node instead needs a separate 128-byte record for every token, metadata alone would be 12.8 GB per node.
If all 100 million tokens have been issued, separate 200-byte initial records require 20 GB for a full copy, before overhead. With purchase-time issuance, unissued capacity does not require 100 million token objects at bootstrap. RAM and bandwidth must be measured on an implemented client. MB and GB here use decimal units.

6. TRANSFER RULES
Status: Design requirements
Reservation, receipt, cancellation, stale data, and transaction identity.

One accepted outcome
A transfer identifies one main-object version, one sender, one recipient, and one transaction identifier. Only the current owner can authorize it. The network must admit at most one conflicting reservation and at most one final outcome for that reservation.
The recipient reconstructs the required current object, verifies the intended parties and reservation, signs receipt, and publishes the resulting state. Gathering enough fragments and producing a signature are required steps; distributed rules must also make the completed outcome uniquely accepted.

State transitions
Starting state | Accepted action | Result
Owned | Reserve a specific transfer | Reserved; unavailable for another spend.
Reserved | Accept recipient-signed receipt | Owned by recipient at a new state version.
Reserved | Accept cancellation under expiry rules | Returned to sender at a new state version.
Credited or cancelled | Replay the old request | No additional transfer or issuance.

Timeout is not automatic rollback
A recipient may lose connectivity after signing or publishing receipt. Lack of an acknowledgement does not prove that receipt failed. A reservation remains unresolved until the protocol establishes receipt or cancellation.
A local timer must not create a second spendable copy. Cancellation and late receipt must be mutually exclusive. The final lifetime, clock tolerance, and recovery procedure are not yet approved.

Replay and retry rules
- Bind signatures to the token version, transaction identifier, network identity, and intended parties.
- Repeat an identical request idempotently; do not issue or credit twice.
- Reject a saved old state once a newer state is accepted.
- Apply transaction limits only after their enforcement and attack model are specified. The proposed ten-attempt identifier limit is a candidate rule, not an implemented network-wide defense.
- Do not treat a new timestamp or a new transaction identifier as authority to bypass an existing reservation.

Status: Project rule · sales not open
Maximum 100 million sun(φ). Initial token price $1, with issuance on completed purchase and the full token price allocated to reserves.

Approved economic parameters
Parameter | Rule
Maximum cumulative issuance | 100,000,000 sun(φ). Unissued capacity is not a treasury token balance.
Initial issuance | No advance mint. Issue only for a completed, confirmed fund purchase.
Initial token price | $1.00 per sun(φ); this is a sale price, not a permanent market-value guarantee.

Supply accounting
Cumulative issued ≤ 100,000,000; available capacity = cap − cumulative issued − committed unissued orders
The 100 million limit is a cap, not an amount already issued. The new rule supersedes the earlier fixed-genesis-inventory proposal. An order can reserve issuance capacity without creating tokens. A completed purchase creates a unique admitted issuance record and releases the tokens to its buyer.
The reference ledger uses whole tokens and integer USD cents for the initial-price phase. Fractional ownership, network token admission and any future price or burn policy still require specifications. No automatic remint allowance is created by a burn.

Purchase completion gates
The reference ledger rejects duplicate payment allocation, changed receipt replay, incomplete backing allocation and cap oversubscription. Its receipt inputs are trusted laboratory facts; it does not verify bank settlement, execute purchases or establish network finality.
- Create an idempotent order binding buyer, quantity and the exact initial-price quote; reserve remaining issuance capacity.
- Verify settled payment of principal plus fees through a trusted payment adapter. A browser request or payment screenshot is not payment evidence.
- Allocate the full token-price principal to settled reserve-asset purchases in the dedicated reserve. Keep fees in separate accounting.
- Record acquired asset quantities, network, reserve destination and unique settlement evidence. Purchase costs and network fees need external operating funding if the full principal is to remain invested.
- Complete issuance once after payment and reserve acquisition conditions are met. An order waiting for acquisition remains pending; it is not represented as a fully backed circulating token.
- If payment or acquisition fails, reconcile before refund or issuance. The local model permits only unpaid cancellation; production refund and recovery require durable atomic accounting.

Primary sale and secondary resale use different fee bases
Primary: buyer = 1.02P; reserve = P; platform = 0.01P; rewards = 0.01P. Resale: seller = 0.98V; platform = 0.01V; rewards = 0.01V.
P is the primary token-price principal before commission. V is a secondary buyer’s all-in platform payment. A primary 2% surcharge is measured against P, not against the $1.02 total. The secondary 2% fee remains included in V.
If all 100 million tokens were sold at the initial price, buyers would pay $102 million: $100 million reserve principal, $1 million platform fees and $1 million reward funding, before separately funded operating costs. This is a full-sale scenario, not current assets or forecast sales.

Backing value is not automatically a one-dollar promise
Estimated net backing per circulating token = (eligible reserve market value − relevant liabilities) / verified circulating supply
The initial $1 purchase allocates $1 of principal to reserve assets. Actual net market value depends on execution prices, costs, asset prices, custody and liabilities. A crypto basket can appreciate or fall after acquisition; neither purchase cost nor a public address guarantees a $1 market price or redemption.
If the initial research basket is 90% USDC and 10% BTC and BTC falls 50% while USDC is unchanged, its value falls 5%: $0.95 per token before other costs, assuming no later issuance. USDC itself can deviate from $1.
Later primary pricing requires a separate policy: issuing at $1 while existing net backing differs from $1 can transfer value between existing and new holders. The initial price does not settle this question. Redemption rights, valuation time and treatment of reserve gains/losses remain launch decisions.

Corporate reserve custody, separate from personal wealth
The reserve is intended to serve token backing, not the founder’s personal spending. 9. FEES & NODE ECONOMICS
Status: 2% sale-fee design
Primary and secondary 2% fees, time-weighted wallet rewards, and conditional operating economics.

Sale-fee rule
Primary: 1.02P = P reserve + 0.01P platform + 0.01P rewards. Resale: V = 0.98V seller + 0.01V platform + 0.01V rewards.
Primary purchases add 2% to the token-price principal: initially $1.02 pays $1 into reserves, $0.01 to the platform and $0.01 to rewards. Platform resales keep the inclusive split: an all-in payment of 100 leaves 98 for the seller, 1 for the platform and 1 for rewards. Reserve principal is not platform revenue.
This is a design decision, not a live collection or payout service. Count completed, eligible, fee-bearing sales once. Do not treat wallet transfers as sales or assume that an off-platform sale is observable. Transfer fees remain a separate open decision. Payment-provider costs, taxes, chargebacks, and payout costs need their own explicit funding policy; they are not silently deducted from the selected 1% node share.

Time-weighted distribution
F = 0.01P + 0.01V; Q = funded sun(φ) pool; T = Σ tⱼ; rewardᵢ = Q × tᵢ / T
For a defined accounting period and settlement currency, P is eligible primary principal excluding the surcharge, V is eligible all-in resale volume, and F is their combined 1% funding allocation. Q is the quantity of existing sun(φ) actually acquired or irrevocably reserved for rewards, not newly minted tokens; and tᵢ is the accepted authorization time of distinct wallet i while connected to the network. T is the sum across all wallets, including i. Every wallet counts separately, including multiple wallets belonging to one operator. Overlapping sessions for the same wallet count once. Token balance does not enter this formula; buying or staking tokens is not a participation requirement.
This is a share of actual fee revenue, not interest on the wallet balance or a fixed annual yield. Zero eligible sales produce zero new rewards. A wallet authorized for half as long receives half the allocation of a full-time wallet within the same period. Authorization time is the chosen reward metric; storage capacity and completed operations do not increase its weight.
The reward asset is selected: sun(φ). Track fee collections separately by payment currency, then distribute a funded token pool. Proposed funding route: purchase already-issued sun(φ) on the market using the 1% allocation. Unissued capacity is not reward inventory; no unpaid reward mint is allowed. Under one effective acquisition price p, Q = F / p; with multiple fills, add the actual token quantities received. The execution venue, pricing rule, conversion-cost policy, and settlement period still require selection.

Accounting proposal and unresolved implementation
- Proposed accounting period: one UTC day, with small earned amounts accumulated until an economical payout. Period length and payout threshold are not yet approved.
- Record accepted authorization intervals bound to a wallet identifier and the network. Merge overlapping sessions of the same wallet and clip intervals to the accounting period. Distinct wallets belonging to one operator remain separate.
- A connected-session protocol must establish authorization start, renewal, logout, and expiry. Proposed short-lived session renewals bound disconnected time; exact renewal and timeout values are not selected. A saved login credential must not count as continuing network presence indefinitely. No fragment-service or storage-volume proof is a reward condition in this selected rule.
- When total accepted authorization time is zero, keep the pool unallocated in a separately recorded reserve; no division by zero or arbitrary beneficiary. Any later release requires an explicit rule.
- Keep sale identifiers, collected fees, eligibility evidence, pool liabilities, and payouts idempotent and auditable. Settlements require integer monetary units and deterministic rounding with all residual units accounted for.
- Release rewards only from funded eligible fees under a defined refund and chargeback policy. UI estimates are not immediately withdrawable funds.

Multiple wallets are explicitly allowed
With equal uptime: operator share = m / (H + m)
The owner explicitly selected per-wallet accounting and intends it to encourage multiple authorized wallets per user. With equal authorization time, an operator with m wallets alongside H other wallets receives m/(H+m) of the pool. At H=10,000 and m=10,000, that share is 50%. Ten distinct wallets receive ten times one wallet’s reward within the same pool. This is permitted behavior, not automatically an attack.
The rule rewards authorized wallet-time, not distinct people, computers, or failure domains. Multiple wallets can contribute storage and service, but wallet counts alone do not measure that contribution or independent availability. Shared hardware and connectivity can fail together. Counterfeiting authorization time or duplicating overlapping time for the same wallet must still be rejected. Reward eligibility does not define voting power or payment acceptance.
Self-trading alone is loss-making under this exact fee rule if an operator captures fraction α of rewards: its net fee loss is (0.02 − 0.01α) × V, at least 1% of its own volume. This assumes no fee rebates, refunds, external incentives, or gains from manipulating prices, and does not limit an operator’s permitted share from multiple authorized wallets.

What operating a node costs
A free-to-join node still consumes disk capacity, memory, bandwidth, CPU time, and electricity. Costs also include synchronization, proof checking, repair after outages, and temporary overlap during recoding.
No measured monthly node cost or guaranteed node income is available. Requirements must distinguish a small bootstrap network from a mature network because storage per holder can differ substantially.

Attack-cost boundary
Expected net payoff = p × G − C; break-even p = C / G
p is the probability that an illicit outcome is actually accepted. G is the realizable gain if it succeeds, before costs C. C is the expected non-recoverable cost for the specified strategy and time window.
With illustrative C=$1,000 and G=$100,000, the break-even probability is 1%. These inputs are sensitivity assumptions, not measured attack economics. Free node entry means a token stake cannot be counted as a mandatory attacker expense.

11. PROBABILITY & CALCULATIONS
Status: Conditional models
Interactive availability estimates, reconstruction thresholds, and explicit assumptions.

Availability is not attack resistance
P(unavailable) = Σ(i=0…k−1) C(n,i) q^i (1−q)^(n−i)
The calculator below measures the chance of lacking enough valid fragments at one snapshot. It does not estimate forged signatures, conflicting receipts, loss of funds, or annual network reliability.
Assume n distinct holders each stores one different, valid fragment of the same accepted version. Each holder independently makes that fragment available with the same probability q. Recovery requires at least k fragments. Shared outages, stale state, malicious withholding, and biased placement violate this model.

Original any-1% requirement
n(N) = N; k(N) = ceil(N / 100)
In the ideal any-k model, at least k distinct valid fragments from the defined generation suffice, regardless of which holders supply them. N=1,000,000 gives k=10,000 and ideal payload expansion n/k=100.
This requirement is stronger than succeeding with high probability for a random surviving subset. A different probabilistic placement model must not silently be presented as the original guarantee.

Search effort
E[queries to find k fragments] = k × (N + 1) / (H + 1)
This expectation assumes uniformly random queries without replacement, H holders of different valid fragments among N discoverable nodes, and H≥k. It excludes timeouts, false responses, stale fragments, and cached locations.
With N=H=1,000,000 and k=10,000, the expectation is 10,000 queries. A full million-node scan is not a universal lower bound. Reconstructing a public token object does not reveal its private key or authorize spending.

Repeated events
Independent attempts: P(at least one success) = 1 − (1 − p)^m
This expression requires m independent attempts with the same success probability p. For T events each with failure probability at most p, the union bound is at most min(1,Tp), without requiring independence.
A per-object, per-snapshot figure is not an annual service guarantee. Real estimates need a defined time horizon, correlation model, placement process, and accepted-state mechanism.

12. SECURITY & THREAT MODEL
Status: Controls to implement
Adversarial behavior, intended defenses, and unresolved security work.

Threat register
Threat | Required control / investigation
Forged authorization | Verify the owner’s signature over canonical, recipient-bound transaction data. Algorithms and implementation require review.
Conflicting transfers | A unique accepted reservation and final outcome across independent nodes; still unresolved.
Sybil identities | Specify how many identities an operator can obtain and how admission or weighting resists concentration. Free node entry alone supplies no bound.
Eclipse or biased discovery | Use diverse discovery paths and test whether an attacker can isolate a recipient’s view.
Replay / stale fragments | Bind accepted versions, transfer IDs, content hashes, and coding generations; reject invalid combinations.
Fragment withholding / mass outages | Test redundancy, repair, independent failure domains, and safe mode below recovery thresholds.
False timestamps | Authenticate records and define clock acceptance; never trust the numerically largest time alone.
Compromised owner key | Protect local keys and backups. Fragmentation cannot undo a valid signature produced with a stolen key.
Flooding and resource exhaustion | Bound message size, verification work, queues, retries, and storage allocation.

What fragmentation protects
Erasure coding can help recover data after some fragments become unavailable. Integrity checks can detect corrupted pieces. Neither property by itself proves ownership, honest peer selection, or exclusive payment finality.
More online identities do not automatically imply more independent operators. Security calculations must state attacker resources and the actual acceptance rule.

Audit and vulnerability reporting
No independent security audit or formal security proof is published. The release process should publish audit scope, findings, fixes, affected versions, and unresolved risks.

13. PRIVACY & ANONYMITY
Status: Threat model
Public keys are pseudonyms. Records, network observations and payment data may connect them to a person.

What can identify or link participants
Information | Observer and possible inference
Owner and recipient public identifiers | Record readers can link reused keys. A key alone does not prove a legal name.
Persistent token ID and history | Record readers can trace ownership changes. Others may archive records beyond the ten-transfer window.
Sending and receipt timestamps | Observers can correlate timing across sources. Precision and publication rules remain open.
IP address and connection timing | Direct peers see network counterparts. NAT, shared computers and relays mean an IP is not proof of a person or original sender.
Amounts, orders and BTC addresses | Exchange records can link both payment legs. The exact public amount representation is not yet defined.
Bank or identity records | Payment providers may associate an order with a customer. This mapping is not inherently public.
Reward authorization and payouts | The accounting service would see wallet session times and payouts. Shared timing may suggest, but not prove, a common operator.

Fragmentation does not establish anonymity
Erasure coding changes data placement; it is not encryption. Anyone who obtains enough valid fragments may reconstruct the public object. More nodes or wallets do not by themselves provide a measurable anonymity guarantee.
Deleting local old data does not delete an observer’s archive. Private-key secrecy protects signing authority, not the unlinkability of public transactions.

Privacy boundaries to implement
- Keep names, email, phone and identity documents out of public token records.
- Separate exchange customer records from public protocol data, with minimal collection and restricted access. The current website has no live wallet or exchange service.
- Separate node transport identities from wallet keys where possible. New wallet keys may reduce reuse but do not erase token-history or timing links.
- Authenticated encryption protects transport against some observers; endpoints still receive the data. Relay-based origin protection needs its own design and testing.
- Stronger transaction confidentiality needs a separate design compatible with validity checks. It is not already delivered by fragmentation.

Current claim: pseudonymity
Full sender or recipient anonymity has not been established. No anonymity percentage is claimed without an implemented protocol, defined adversary and measurements.
Bitcoin’s privacy guidance provides a useful comparison for address reuse and external identity links; it is not evidence of SunPhi’s implemented properties.

14. RUN A NODE
Status: Preparation guide
Startup, resource planning, synchronization, and shutdown behavior.

Before installation
The first client is planned for Windows. No installer or public testnet endpoint is available yet. Minimum CPU, RAM, disk, operating-system version, and bandwidth will be published after benchmarks.
A node must be able to start without a token balance. A node identity and a wallet’s spending key serve different purposes; storage participation should not require revealing wallet secrets.

Planned operating sequence
- Verify the release version, checksum, and publisher signature.
- Create or load a node identity and configure resource limits.
- Discover peers through more than one route and verify the accepted network configuration.
- Synchronize current state and reconcile existing fragments before cleanup.
- Monitor usable fragments, repair backlog, disk use, and connectivity.
- Shut down safely; on restart, verify freshness before serving or deleting retained data.

When the network contracts
Outages, software defects, participant withdrawal, and network partitions can reduce reachable holders. Reconstructability depends on the original coding threshold and the availability of distinct valid fragments.
Do not lower an old threshold in place. Recover, recode, verify the replacement, and switch generations safely. If the network cannot establish current state or reconstruct required data, the intended behavior is to pause affected transfers rather than create an unsupported credit.

Connection and conversion
The SunPhi wallet and website connection protocol have not been released. This site holds no connected account, balance or signing session. The intended flow is: connect a selected wallet, review a conversion offer, then approve the exact operation in the wallet.

A wallet is not a fragment collection
A wallet manages authorization keys and displays accepted token state. A fragment holder stores data. Anyone able to reconstruct a public object must still provide the owner’s valid authorization before spending.
The address format, key derivation, backup format, and hardware-wallet support have not been selected. No recovery phrase should be generated or entered on this website.

Planned wallet behavior
- Show spendable, reserved, received, and unresolved states separately.
- Confirm the recipient and amount before signing.
- Show a completed receipt only after the protocol’s acceptance rule is satisfied.
- Keep a pending transfer visible through outages and recovery.
- Support verifiable backups and explicit recovery instructions before holding real funds.

Privacy and recovery limits
Publicly distributed token records may expose transaction relationships. No anonymity guarantee or implemented privacy protocol is claimed.
Losing a signing key may make assets inaccessible. A key-recovery or reversal authority has not been specified. Backups and recovery tests are part of the release requirements, not an available recovery service today.
